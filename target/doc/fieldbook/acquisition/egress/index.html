Egress policy: how collection traffic leaves the process.

Direct networking remains the default. An explicitly configured proxy is considered only for a route the account holder is, by the venue’s terms, eligibility rules, and applicable law, permitted to use. A proxy is a network path, not an entitlement to access a venue, and this module must never be used to disguise a client’s location or bypass a restriction.

Properties enforced here:

  • Rights before routes. No HTTP client is built until the runtime authorization source has granted a live, venue-scoped right. A proxy is a route, never an entitlement.
  • Fail closed. In explicit_proxy mode, a proxy that cannot be reached or negotiated fails the connection. There is never a silent fallback to direct egress.
  • Direct stays direct. Direct mode never inherits unrelated shell proxy variables; the explicit route is the only route that is added, and the HTTP client is built with no_proxy before the explicit route is applied.
  • Secrets stay in the environment. Proxy endpoints and credentials are read from environment variables named by [network] in configuration, never from the TOML document itself. They are never serialized, hashed into fingerprints, written to logs, or embedded in error messages.
  • Venue authentication is end-to-end. Adapter signatures and venue TLS credentials are only ever sent through the venue’s TLS connection. A proxy observes destination metadata; it is not a trust anchor.

See ADR 0002 for the policy and the evidence provenance contract.
